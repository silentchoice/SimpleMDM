# SimpleMDM 业务数据录入与审批设计

## 目标

在现有元数据驱动的管理控制台中增加完整的业务数据录入能力。部门编辑人通过动态表单维护一条主数据及其全部子数据，保存草稿并提交审批；部门审批人批准后，主子数据在同一数据库事务中生效。系统同时补齐仪表盘、模块化表格界面、业务数据审批、编码规则、编辑锁、跨部门共享和有限版本历史。

## 范围与约束

- 新增、修改和逻辑删除均遵循“草稿 → 提交审批 → 审批通过后生效”。
- 一条主数据及其全部子数据是单个草稿、审批任务和生效事务的边界。
- 每条正式记录只保留最近 3 个已生效历史版本。
- 使用 Redis 30 分钟排他编辑锁，并以数据库版本号作为并发保护的第二道防线。
- 本部门查看完整数据；跨部门只能查看元数据中标记为共享的字段。
- 主数据编码由主类型级规则生成，第一版支持固定文本、`{yyyyMMdd}` 和固定位数流水号。
- 复用现有审批中心和 `approval_tasks`，但元数据审批行为保持不变。
- 新增界面延续默认简体中文及运行时中英切换。

不在本期范围：通用工作流设计器、多级审批、条件分支编码表达式、物理删除、无限历史、导入导出和同步模块改造。

## 架构与模块边界

新增独立后端 `record` 模块，负责业务记录、草稿、动态值校验、编码生成、可见性、版本历史和编辑锁。元数据模块继续作为字段结构的唯一来源；审批模块协调任务状态，但业务记录快照的验证与生效由记录模块负责。

端到端流程为：

`动态录入表单 → 保存完整主子草稿 → 获取/续期 Redis 锁 → 提交审批 → 现有审批中心 → 单事务生效 → 清理为最近 3 个历史版本`

主要模块职责：

- 元数据模块：提供部门当前已生效的主字段、子类型和子字段定义。
- 记录模块：提供正式记录查询、草稿 CRUD、动态校验、逻辑删除、编码生成、编辑锁和历史查询。
- 审批模块：在现有任务中增加明确的业务数据任务类别，负责部门级审批权限和状态转换。
- 前端业务数据模块：以表格为入口，使用动态主表表单和子表行编辑器维护完整草稿。
- 前端审批中心：按元数据与业务数据分类，共用列表入口，详情渲染各自的安全差异视图。

## 数据模型

### 正式记录

- `master_records` 保存部门、主类型、系统编码、动态主字段 JSON、状态、当前版本、创建/更新审计字段。
- `sub_records` 保存所属主记录、子类型、动态子字段 JSON、行顺序、状态和审计字段。
- 正式记录使用逻辑删除状态。普通列表默认排除已删除记录，并提供“包含已删除数据”筛选。

### 草稿与审批快照

- `master_record_drafts` 表示一次完整主子变更，关联新增、修改或删除动作以及目标正式记录。
- `sub_record_drafts` 保存该草稿下全部子记录的期望状态，包括新增行、修改行、删除行和排序。
- 草稿状态为 `DRAFT → PENDING → APPROVED | REJECTED`。
- 被拒绝的草稿和审批审计保持不可变；编辑人可将其复制为新草稿后修改并重新提交。
- 提交后草稿内容冻结，直到审批结束，不能原地修改。

### 历史版本

- 审批修改或删除前，将当前正式主记录和全部子记录写成一个整体历史快照。
- 审批新增后，正式记录从版本 1 开始；后续每次批准使版本递增。
- 每条主记录仅保留最近 3 个历史快照。新快照写入后，在同一事务中删除超出上限的最旧快照。
- 历史用于查看和审计，本期不提供一键回滚。

### 编码规则

- 超级管理员按主类型配置编码模板和流水号宽度，例如 `CUS-{yyyyMMdd}-{0001}`。
- 第一版仅允许固定文本、一个日期变量和一个流水号段；保存规则时进行语法及示例预览校验。
- 序号按“主类型 + 日期”独立递增，通过数据库事务行锁保证并发唯一。
- 新记录第一次成功保存草稿时预占最终编码。
- 草稿删除或审批拒绝后编码不回收，防止历史引用和编码重用。

## 动态字段与子表

- 主字段和子表字段统一支持文本、数字、日期、日期时间、选择、单选、多选和开关类型。
- 后端按当前 ACTIVE 元数据校验未知字段、必填、类型、选项、重复字段和非法值。
- 子类型在录入抽屉中显示为独立标签页；每个子类型使用可增行、删行和排序的表格编辑器。
- 子表的所有行和顺序随主记录整体保存与审批，不能独立生效。
- 主字段及子表字段的编辑抽屉都提供“跨部门共享”开关，默认关闭。
- 元数据列表统一显示字段编码、显示名称、数据类型、必填、共享、顺序和操作。
- 数据类型和共享属性属于元数据变更，审批通过后才影响业务录入与展示。

## 权限与共享

- `DEPT_EDITOR` 只能新增、修改、逻辑删除本部门业务数据，保存草稿并提交审批。
- `DEPT_APPROVER` 只能审批本部门任务，且不能审批自己提交的任务。
- `DEPT_VIEWER` 只读。
- `SUPER_ADMIN` 配置主类型、编码规则、字段和部门分配，默认不代替部门角色录入或审批。
- 本部门用户可查看完整主字段和全部子数据。
- 跨部门访问必须由后端过滤，只返回标记为共享的主字段和子表字段，不能仅依靠前端隐藏。
- 某条子数据没有任何共享字段时整行不返回；存在共享字段时只返回这些共享字段值。
- 任何用户都不能编辑其他部门的数据。

## 编辑锁与并发

- 编辑正式记录或已有草稿前获取 Redis 排他锁，默认租期 30 分钟。
- 编辑页面存续期间定时续期；保存、提交、取消和正常离开页面时主动释放。
- 锁由记录、部门、持有者和不可猜测令牌标识；续期和释放必须验证持有者及令牌。
- 锁冲突时返回锁定人和到期时间，其他用户只能查看。
- 提交和审批时仍校验数据库版本号，Redis 锁异常失效也不能造成旧版本覆盖新版本。

## API 与审批集成

记录 API 分为正式数据查询、草稿、锁、历史和编码规则接口族。路径中的部门、记录和主类型 ID 是权威标识，请求体不得覆盖路径身份；服务端从登录身份推导当前部门和操作者。

业务草稿提交后，在现有 `approval_tasks` 中创建业务数据类别任务。审批详情通过任务 ID 读取绑定快照，不接受客户端传入任意快照。批准时在一个事务中完成：

1. 锁定审批任务及目标记录。
2. 再次校验部门、审批角色、非本人审批、任务状态、元数据兼容性和目标版本。
3. 写入旧正式数据的整体历史快照。
4. 将完整主子草稿应用到正式表，或执行逻辑删除。
5. 将正式版本递增并清理超出 3 个的旧历史。
6. 更新草稿和审批任务状态，记录审批人、意见和时间。
7. 提交事务后释放编辑锁。

任一步失败则全部回滚。拒绝只更新审批与草稿状态，不改变正式数据。

## 前端信息架构

界面保持模块化，不把所有功能堆在一个页面：

- 仪表盘：仅展示正式数据数、我的草稿、待我审批、本月生效数、最近任务和权限相关快捷入口。
- 业务数据：独立菜单与表格页面，支持主类型、编码、关键字、状态、更新时间筛选及分页。
- 元数据管理：继续独立，主字段、子类型和子表字段分标签；补齐子表字段的数据类型与共享控制。
- 审批中心：一个菜单，列表增加“元数据 / 业务数据”分类；列表与详情分离。
- 系统管理：保持现有用户、部门和角色页面。

业务数据新增或编辑使用独立抽屉。上部是动态主字段表单，下部按子类型分标签，每个标签是可编辑行表格。编码只读显示，首次保存草稿后展示预占编码。草稿允许反复保存，提交前执行完整校验；审批中的记录不可再次编辑。

逻辑删除要求填写删除原因并生成删除草稿。详情页包含当前数据、草稿差异和最近版本三个标签。审批详情顶部使用横向单行信息流，下面以表格展示主字段及子表逐行差异。

## 错误处理

- Redis 锁冲突显示锁定人和到期时间。
- 版本冲突要求刷新后重新编辑，绝不静默覆盖。
- 编码规则错误、动态字段校验失败、任务状态冲突和重复提交返回明确业务错误及请求 ID。
- 后端消息保持原样，前端只翻译自身标签和请求 ID 包装。
- 保存、提交、批准和拒绝均防重复点击。
- 非法或旧版审批快照安全降级为只读原始数据，不使用 HTML 注入渲染。

## 测试与验收

后端单元测试覆盖动态字段校验、编码解析、并发流水号、草稿状态机、逻辑删除、最近 3 版清理、共享过滤及锁令牌验证。集成测试覆盖完整主子保存与生效事务、拒绝后复制、锁生命周期、版本冲突、部门隔离和角色权限。

前端测试覆盖动态主表、子表逐行录入、各数据类型控件、共享开关、草稿操作、列表筛选分页、删除原因、审批分类、横向流程、差异表、仪表盘角色视图及中英切换。现有元数据审批必须完整回归。

最终验收场景：编辑人录入一条包含多条子数据的记录，保存草稿并提交；审批人查看横向轨迹和主子差异后批准；正式数据原子生效；跨部门用户只能看到共享字段；连续审批修改后历史始终最多保留最近 3 版。
