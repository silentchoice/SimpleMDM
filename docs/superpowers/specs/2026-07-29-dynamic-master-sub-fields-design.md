# SimpleMDM 主子表完全动态字段设计

## 目标

消除部门主数据页面与字段定义之间的不一致，使字段定义成为主表和子表业务字段的唯一来源：

- 主表允许新增任意业务字段。
- 子表允许新增任意字段组、字段和记录。
- 字段改名不破坏已有数据。
- 前后端使用同一套字段类型、校验和显示规则。
- 部门权限、审批流程和多系统隔离继续有效。

本次允许数据库在启动时重建，不提供旧表在线迁移。

## 总体方案

采用“系统列 + JSON 业务数据”的统一动态模型。

主表保留身份、隔离、权限、状态和审计所需的系统列，所有普通业务字段存入 `data_json`。子表继续使用 JSON 存储，但与主表共用字段定义规范和动态表单行为。

字段定义同时保存不可变的 `field_key` 和可修改的 `field_name`：

- `field_key` 是 JSON、接口、搜索、校验及审批差异使用的稳定标识，创建后不可修改。
- `field_name` 是用户界面显示名称，可以修改。

例如，把 `employee_code` 的显示名从“工号”改为“员工编号”时，已有 JSON 数据无需迁移。

## 数据模型

### `mdm_personnel`

保留以下系统列：

- `id`
- `system_code`
- `owner_dept`
- `data_json`
- `status`
- `version`
- `created_at`
- `updated_at`

原有 `employee_code`、`name`、`gender`、`department`、`position`、`phone` 和 `email` 等业务列不再单独保存，统一进入 `data_json`。

`owner_dept` 是权限和审批使用的系统属性，不存入 `data_json`。界面通过不可删除的系统字段定义展示和编辑它。

### `mdm_personnel_sub`

保留：

- 主记录 ID
- `system_code`
- `sub_type`
- `owner_dept`
- `data_json`
- `visibility`
- `version`
- 创建及更新时间

子表字段值一律以 `field_key` 作为 JSON 键。

### `mdm_field_definition`

字段定义包含：

- `system_code`
- `department`
- `table_type`：`master` 或 `sub`
- `sub_type`
- `field_key`
- `field_name`
- `field_type`
- `required`
- `sort_order`
- 字段选项
- 创建人和审计时间

约束：

- 同一作用域内 `field_key` 唯一。
- `field_key` 创建后不可修改。
- 主表的 `owner_dept` 是不可删除的系统字段。
- 字段定义不执行物理删除。
- 已有数据不兼容时，拒绝修改字段类型。

## API 与数据流

### 主数据

主数据接口返回系统属性和动态数据：

```json
{
  "id": 1,
  "system_code": "HR",
  "owner_dept": "工程部",
  "status": "active",
  "version": 1,
  "data": {
    "employee_code": "EMP001",
    "name": "张三"
  }
}
```

新增和编辑请求使用相同结构。后端根据当前 `system_code` 的主表字段定义执行白名单、必填及类型校验；未知字段会被拒绝。

主数据列表按主表字段定义动态生成列。部门过滤继续使用 `owner_dept`，关键字搜索在字段定义允许的动态字段中匹配。

### 字段定义

创建字段必须提供唯一的 `field_key`。创建后只能修改显示名、类型、必填、排序和选项。

主表字段定义跨部门共享，子表字段定义按 `system_code + department + sub_type` 隔离。

### 子表

创建至少一个子表字段后，主数据详情立即展示相应空字段组和“添加记录”按钮。新增或编辑记录时，页面按字段定义生成表单，后端按相同定义再次校验。

## 前端结构

建立共用的动态字段渲染能力，由主表和子表共同使用：

- 文本
- 数字
- 日期
- 下拉
- 单选

该能力负责：

- 根据 `field_key` 绑定数据。
- 使用 `field_name` 显示标签。
- 生成必填和类型校验。
- 解析字段选项。
- 在查看、编辑和列表模式中保持一致。

主数据表单和列表不再硬编码业务字段。

## 权限与审批

- `owner_dept` 是主表和子表编辑权限的权威依据。
- 用户必须拥有当前 `system_code` 和 `owner_dept` 对应的 `EDIT` 权限。
- 主表变更继续进入现有审批流程。
- 审批变更数据使用 `field_key` 保存，界面按当前字段定义的 `field_name` 展示。
- 本次子表新增和编辑仍直接保存；子表审批作为后续独立任务处理。

## 校验和错误处理

后端拒绝：

- 未在字段定义中出现的业务字段。
- 缺少必填字段。
- 数字、日期或选项类型不匹配。
- 重复的 `field_key`。
- 无权限的部门或系统。
- 不存在的子表字段组。
- 会使已有数据不兼容的字段类型修改。

接口返回可定位到具体 `field_key` 的明确错误信息。前端预校验用于即时反馈，后端校验作为最终保障。

## 数据重建与种子数据

项目处于可重建数据库的 Demo 阶段。本次直接更新表结构和种子数据，不保留现有数据，也不编写旧表在线迁移。

所有种子主数据和子表 JSON 键必须与对应字段定义的 `field_key` 完全一致。

## 测试策略

覆盖以下场景：

- 新增主表自定义字段后，新增、查看、编辑和列表展示一致。
- 字段显示名修改后，已有数据继续显示。
- 主表审批差异使用稳定键保存、显示名展示。
- 新增子表字段组、字段及多条记录。
- 文本、数字、日期、下拉、单选和必填校验。
- 未知字段与不兼容字段类型修改被拒绝。
- 同部门编辑、跨部门只读。
- 不同 `system_code` 的字段和数据相互隔离。
- 数据库重建后种子数据与字段定义一致。

## 范围边界

本次包含主子表动态字段改造、动态表单/列表、后端校验和种子数据重建。

本次不包含：

- 旧数据在线迁移。
- 子表新增或编辑审批。
- 字段物理删除。
- 通用 EAV 数据引擎。
