# 部门主数据选择与主子表可见性设计

## 关联设计

本文补充
[`2026-07-30-field-isolation-sharing-deletion-design.md`](./2026-07-30-field-isolation-sharing-deletion-design.md)，
规定部门主数据模块的部门选择、页面状态、查看权限和共享子表展示行为。

## 目标

当前部门主数据列表默认混合展示多个部门，现有部门筛选只是可清空的查询条件，容易造成上下文混乱。本次改造将部门变成模块的必选上下文：

- 进入模块时必须选中一个部门。
- 默认选中当前用户所属部门。
- 不提供“全部部门”。
- 用户只能切换到拥有 `VIEW` 权限的部门。
- 所属部门可编辑，其他部门只读。
- 所有可查看部门的主表完整可见。
- 其他部门的子表只返回字段定义中 `shared=true` 的字段和值。

## 部门上下文与 URL

部门主数据列表使用 URL 查询参数保存选中部门：

```text
/personnel?department=工程部
```

规则如下：

1. URL 部门存在且用户拥有该部门 `VIEW` 权限时，使用 URL 部门。
2. 否则，若用户拥有所属部门 `VIEW` 权限，默认使用所属部门。
3. 否则选择第一个可查看部门。
4. 用户没有任何可查看部门时，显示“暂无可查看部门”，不请求人员列表。
5. 切换部门时更新 URL、重置页码、清空旧列表并请求新部门数据。
6. 不允许空部门请求，也不提供“全部部门”选项。

选中部门是列表、详情导航和新增/编辑操作的唯一页面上下文。刷新页面或从详情返回时必须恢复该部门。

## 前端列表交互

部门选择器位于模块标题区域，作为醒目的必选下拉，而不是普通可清空筛选项。

- 下拉选项仅包含后端返回的可查看部门。
- 搜索框只在当前选中部门内搜索。
- 选择其他部门后，列表进入只读状态。
- 只有选中当前用户所属部门时才显示“新增”按钮。
- 只有当前用户所属部门的记录显示“编辑”按钮。
- 切换部门时立即清空上一部门数据并显示加载状态。
- 连续快速切换时，只接受最后一次请求结果；已过期请求不能覆盖当前部门列表。

新增页面固定使用当前用户所属部门，不提供可编辑的所属部门选择器。用户不能通过请求参数或修改请求体向其他部门新增主数据。

## 详情导航

从列表打开详情或编辑页时携带来源部门：

```text
/personnel/12?from_department=工程部
/personnel/12/edit?from_department=工程部
```

- 返回按钮回到 `/personnel?department=<来源部门>`。
- 来源部门缺失或无权查看时，按列表默认部门规则回退。
- 详情页权限以人员记录真实所属部门为准，不能信任 `from_department`。
- 当前所属部门人员允许编辑主表和维护子表。
- 其他部门人员只读，不显示主表编辑、子表新增或子表编辑操作。

## 后端部门查询与鉴权

人员列表接口要求非空 `department`：

```text
GET /api/personnel?department=工程部
```

后端行为：

1. 查询当前用户可查看部门。
2. 请求部门不在可查看集合中时返回 403。
3. 仅查询指定部门，不支持空部门代表全部数据。
4. 系统隔离条件继续生效。

部门下拉接口只返回用户在当前系统内拥有 `VIEW` 权限的部门。不能把字段定义中出现过的部门或人员表中的全部部门直接暴露给无权用户。

人员详情接口在按 ID 查询后，使用人员真实 `owner_dept` 执行 `VIEW` 权限校验。无权限时返回 403，避免用户通过直接输入 ID 越权查看。

新增和编辑接口继续执行 `EDIT` 校验，并额外约束：

- 新增记录的 `owner_dept` 必须等于当前用户所属部门。
- 修改记录时，原部门和目标部门都必须等于当前用户所属部门。
- 不存在跨部门编辑或调动能力。

## 主表可见性

主表字段按系统全局共享。只要用户拥有目标部门 `VIEW` 权限：

- 返回完整主表字段定义。
- 返回人员完整主表 JSON 数据。
- 不因切换到其他部门而隐藏主表列或值。

主表可见不代表可编辑；其他部门的主表始终只读。

## 子表共享可见性

子表共享遵循字段定义级 `shared`，不再使用记录级 `visibility`。

查看当前用户所属部门人员时：

- 返回该部门全部子表字段定义。
- 返回对应的全部子表 JSON 值。
- 允许新增和编辑子表记录。

查看其他部门人员时：

- 只返回该部门 `shared=true` 的子表字段定义。
- 每条子表记录的 `data` 只包含共享字段对应的键和值。
- 不返回非共享字段名称和值。
- 若字段组没有任何共享字段，则不返回该字段组及其记录。
- 子表记录全部只读。

过滤必须在后端完成。前端仅渲染后端授权后的字段和值，不能先获取完整数据再隐藏列。

## 接口响应建议

人员详情响应保持主表与子表职责分离。字段定义接口和子表记录接口必须使用相同的可见性判断，避免返回字段但没有值，或返回值但没有字段定义。

后端可在共享字段过滤服务中统一计算：

```text
viewerDepartment == ownerDepartment
  ? 所有字段
  : shared=true 的字段
```

同一结果同时用于：

- 子表字段定义响应。
- 子表记录 JSON 键过滤。
- 空字段组判断。

## 异常处理

- 列表部门为空：返回 400，“必须选择部门”。
- 列表部门无查看权限：返回 403，“无权查看该部门主数据”。
- 详情人员不存在：返回 404。
- 详情人员所属部门无查看权限：返回 403。
- 向其他部门新增或编辑：返回 403，“只能维护所属部门主数据”。
- URL 部门无效：前端回退到默认可查看部门，不展示旧部门数据。
- 没有可查看部门：前端展示空状态，不触发列表请求。

## 并发请求处理

部门切换会产生新的列表请求。前端为每次请求记录序号或使用取消机制：

- 新请求开始时清空当前表格。
- 只有最新请求可以写入列表和总数。
- 旧请求即使后返回，也必须丢弃。

搜索、分页和部门切换共用同一请求保护逻辑。

## 测试策略

前端测试覆盖：

- 默认选中当前用户所属部门。
- URL 中合法部门优先于默认部门。
- URL 部门无权查看时回退到默认部门。
- 下拉只包含可查看部门且没有“全部部门”。
- 切换部门会更新 URL、重置页码并清空旧数据。
- 其他部门隐藏新增和编辑操作。
- 当前所属部门允许新增和编辑。
- 返回详情后恢复来源部门。
- 无可查看部门时展示空状态且不发列表请求。
- 快速切换部门时旧请求不能覆盖新数据。

后端测试覆盖：

- 列表拒绝空部门。
- 列表拒绝无 `VIEW` 权限部门。
- 列表只返回指定部门数据。
- 部门下拉只返回可查看部门。
- 详情按人员真实所属部门执行查看权限校验。
- 直接输入无权限人员 ID 返回 403。
- 新增和编辑拒绝其他部门。
- 本部门详情返回完整主表和全部子表字段值。
- 其他部门详情返回完整主表，但只返回共享子表字段和值。
- 没有共享字段的子表组不出现在响应中。

## 验收标准

- 部门主数据模块始终具有一个明确选中的部门。
- 页面不再混合展示多个部门人员。
- 刷新、分页、搜索和详情返回均保持选中部门。
- 用户无法从下拉框或接口查看没有 `VIEW` 权限的部门。
- 用户只能新增和编辑自己所属部门的主数据。
- 所有可查看部门的主表字段和值完整可见。
- 其他部门的非共享子表字段名称和值不会发送到前端。
- 其他部门的共享子表字段和值能够正常展示。
- 页面不再出现记录级可见性控件。
